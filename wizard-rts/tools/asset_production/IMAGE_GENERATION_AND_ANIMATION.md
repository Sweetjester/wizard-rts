# How The Kon Images And Animations Were Made

Technical production reference, 2026-09-06. Read with [the handbook](README.md).
This file explains the actual implementation, distinguishes it from suggested
future improvements, and gives another coding agent a reproducible procedure.

## 1. The Central Idea

The image generator supplied painted raster artwork. Godot scripts supplied
assembly, articulation, timing, frame rendering and gameplay integration.

For units:

```text
User reference + production prompt
    -> generated painted source PNG
    -> inspected regions, masks and joints OR selected complete poses
    -> deterministic Godot puppet
    -> transparent offline frame rendering
    -> runtime sprite atlases
    -> ArtSprite state selection
    -> Sprite2D and shared Sprite3D billboard presentation
```

For buildings:

```text
User reference + exact gameplay envelope
    -> painted production textures + authored 3D architectural geometry
    -> skin attached to the existing YAML-driven structure builder
    -> independently authored navigation, collision, gates and sockets
    -> real-map construction and traversal verification
```

There is no image-generation dependency in the running game. The generated
source is not itself a finished animation, navigation mesh or 3D model.

## 2. Image Generation: Tool, Inputs And Limits

The artwork in this workflow was produced with the assistant's built-in image
generation tool, using the user's attached concept art as a visual reference.
It was not painted by a GDScript drawing routine, trained from scratch, or
generated by the separate Blender unit pipeline in this repository.

The exact backend model identifier/settings are not established by the source
files. Do not invent a model name, seed or API configuration. Tool access in
one assistant does not mean another LLM automatically has that tool. A worker
needs its own authorized image-generation interface or pre-generated artwork.

Reference paths from a user's temporary clipboard folder are not durable asset
storage. For a future task, preserve an authorized reference copy with the task
inputs, record its origin and keep the original generated result unchanged.
Record the exact prompt, tool/model metadata when actually supplied, output
dimensions and subsequent cleanup. Do not assume generated pixels reproduce
exactly on another run. Rebuilding from the saved source is the reliable path.

### Art Direction Supplied To The Generator

Sinister fantasy board-game miniature, sculpted wood/clay/stone character,
hand-painted illustrated texture, bold dark ink contours, chipped uneven
surfaces and clear silhouettes. Kon's references establish blue-grey/teal
materials, cyan magic, charcoal framing and burgundy/coral organic accents.

The anatomy and silhouette come from each reference. The Spawner's brood
abdomen is not interchangeable with the Mangler's gorilla-like forelimbs.
Do not reduce the style instruction to "make it cyan".

### Parts Sheet Versus Pose Sheet

Choose before requesting art:

- Parts sheet: separate painted body components that will rotate around joints.
  Used by Oaven and Spawner. Ask for complete attachment ends and overlap margin.
- Pose sheet: several complete character silhouettes at important action beats.
  Used by Mangler and Kon. Ask for fixed camera, anatomy, clothing and lighting.
- Segmented source: repeated articulated sections for length/stage changes.
  Used by the Serpent, with separate wall presentation assets.

Do not ask vaguely for "an animated sprite sheet" and expect coherent frames,
exact grids, correct pivots and transparent borders to emerge automatically.

### Concrete Spawner Prompt

The actual saved generation prompt is [art_prompt.txt](../spawner/art_prompt.txt).
It requested twelve independent components in a four-column, three-row layout:
abdomen, thorax, head, antennae, upper leg, lower leg/foot, forewing, hindwing,
artillery siphon, open brood hatch, small brood insect and closed hatch.

It specified a right-facing three-quarter RTS view, the supplied concept's pale
carapace/burgundy underside/cyan wings, generous nonoverlapping margins and a
uniform magenta background. The requested resolution was 2048x1536; a requested
resolution is not proof of the returned file's actual dimensions. The puppet's
authored PARTS rectangles describe the image that was actually used.

For a new creature, reuse this specificity, not the Spawner's anatomy or pixel
coordinates. A reusable prompt scaffold is in [UNITS.md](UNITS.md).

## 3. Source Inspection And Background Removal

Check the downloaded/saved image before rigging:

1. Actual width, height and alpha content.
2. All limbs, weapons and wings fully included.
3. Consistent form and camera between poses.
4. No neighbouring parts intruding into a region.
5. Enough joint overlap to avoid holes when rotated.
6. No background, lettering or ground shadow accidentally part of the silhouette.

A drawn checkerboard is opaque artwork, not transparency. Oaven's source
required a follow-up edit to replace a baked checkerboard with magenta. Spawner
explicitly requested magenta. Other source assets can use real transparency.

### Existing Chroma Shader

[chroma_key.gdshader](../oaven/chroma_key.gdshader) is an offline canvas shader:

```glsl
float key = min(c.r, c.b) - c.g;
float alpha = 1.0 - smoothstep(0.10, 0.30, key);
```

It makes magenta-dominant source pixels transparent and retains the source
alpha and part tint. It is not semantic background segmentation. It may also
remove genuine magenta paint, and it does not perform sophisticated color
decontamination. Inspect fringe pixels on light and dark backgrounds. Prefer
true alpha for new source art when the generator produces it correctly.

The key shader is applied during baking. Runtime atlases already contain alpha;
live units do not need this shader or the original key-colored source.

### Region Maps Are Authored, Not Assumed

Spawner's PARTS array contains twelve individually measured rectangles.
Mangler's REGIONS array contains sixteen nonuniform rectangles. Some Mangler
poses use polygon UV outlines to exclude fragments at neighbouring corners.

These coordinates are tied to the saved source pixels. Regenerating a source
requires remeasuring them. Dividing every new sheet into an equal grid without
inspection is a common cause of missing feet and floating fragments.

## 4. Articulated Cutout Animation: Spawner Example

Implementation: [spawner_puppet.gd](../spawner/spawner_puppet.gd).

The offline puppet extends Node2D. It accepts an action and normalized phase.
Its drawing code computes deterministic transforms, then draws painted texture
regions in a deliberate order. It is a code-authored 2D puppet, not a rigged
mesh or automatic AI motion system.

### Hierarchical Joints

The existing helper composes a child transform with its parent:

```gdscript
return parent * Transform2D(angle, point)
```

A knee follows the upper leg's transform; the upper leg follows the body.
The head and antennae are attached similarly. Source regions are drawn into
local rectangles chosen so the painted joint aligns with the local origin.
Transform pivots and source rectangles solve different problems: a correct
crop alone will not make a limb rotate around its shoulder.

### Layer Order And Depth

Far legs are drawn first and darkened. Abdomen, thorax and near legs follow.
Wings, head, antennae and ability details are layered intentionally. This gives
the illusion of depth without a 3D skeleton. Check action extremes; a draw
order that works in idle may put a leg over the wrong part during a cast.

### Motion Functions Actually Used

- phase * TAU defines a repeating cycle.
- Sine offsets give alternating leg motion, breathing and antenna sway.
- Three leg pairs use phase offsets to avoid moving all feet together.
- smoothstep controls root/unroot stance, wing spread and death progression.
- A short exponential pulse supplies artillery recoil.
- A sine-shaped summon envelope opens the hatch and swells the abdomen.
- Flying poses spread and foreshorten the painted wings at their roots.
- Death bends limbs, lowers/tilts the body and reduces selected part brightness.

The brood insect drawn in the summon animation is presentation. Actual drone
creation remains gameplay's responsibility. This distinction prevents a
beautiful animation from silently changing unit counts or costs.

These motions are hand-authored formulas and timings. They are not physical
foot placement, inverse kinematics or independently painted animation frames.

## 5. Key-Pose Animation: Mangler Example

Implementation: [mangler_puppet.gd](../mangler/mangler_puppet.gd).

The saved source contains sixteen complete painted poses across base and
evolved forms. The puppet selects a pose for the action and adds controlled
movement. It does not split every pose into skeletal components.

Examples in the current implementation:

- Idle: approximately one-percent breathing squash.
- Run: alternating two painted poses plus a small vertical bob.
- Attack: windup pose, contact pose, then return to idle; a forward shift helps
  the strike read. Pose thresholds are explicit in code.
- Hurt: a selected crouched pose with a brief lean.
- Leap windup: compression; airborne: dedicated pose; landing: squash recovery.
- Evolution: restrained scale growth in the chosen form.
- Death: an initial collapse pose followed by a flattened corpse pose.

Each silhouette is fitted within a padded 384px frame. The frame has a fixed
ground anchor rather than centering every pose independently. Some pose-specific
fit heights remain artistic choices; inspect transitions for unwanted popping.

Large new motions require new source poses. Stretching an idle pose is not a
substitute for a convincing strike, rear view or death. More baked samples can
smooth transforms but cannot invent missing anatomy or intermediate drawings.

## 6. Offline Sprite Baking

Examples: [bake_spawner.gd](../spawner/bake_spawner.gd) and
[bake_mangler.gd](../mangler/bake_mangler.gd).

### Rendering Sequence

1. Create a SubViewport with transparent_bg=true and disable_3d=true.
2. Add the puppet with the intended position and scale.
3. Allocate an RGBA8 Image for the complete atlas.
4. Set the action/form and sample phase for each output frame.
5. Request redraw, await a process frame, then RenderingServer.frame_post_draw.
6. Read the viewport texture into an Image.
7. Downsample if required and blit into the atlas cell.
8. Save PNG, check success and reimport into Godot.

Without the frame waits, a baker can capture old/blank data. The baker requires
a graphical renderer. Headless is appropriate for many validation scripts but
not a replacement for actual raster baking or screenshot inspection.

### Phase Sampling

For twelve looping samples, frame/12 gives 0 through 11/12 and avoids a duplicate
endpoint. For a twelve-sample one-shot, frame/11 includes the final state at 1.
Existing bakers classify actions explicitly. Do not treat every new action as
looping simply because it has twelve cells.

The baker's sample count and the runtime action duration are separate. Twelve
frames can play over different durations. The presentation code must map the
actual gameplay phase or event age to the intended frame.

### Supersampling And Portraits

Spawner renders at 768x768, then uses Lanczos downsampling to 384x384. Its puppet
position is (384,620), which becomes the final foot anchor (192,310). It renders
a separate portrait composition rather than enlarging a small frame.

Mangler renders directly at 384x384 and saves the first base frame as portrait.
These are two actual approaches, not a universal portrait requirement.

### Existing Asset Contracts

| Asset | Frame | Atlas per sheet | Rows / columns | Sheets / forms |
| --- | --- | --- | --- | --- |
| Oaven | 256x256 | 3072x3840 | 15 / 12 | Two sheets, base/Jumper |
| Spawner | 384x384 | 4608x6144 | 16 / 12 | One shared sheet |
| Kon | 384x384 | 4608x3072 | 8 / 12 | One hero sheet |
| Mangler | 384x384 | 4608x3456 | 9 / 12 | Two sheets, base/winged |

Serpent has six stage atlases with nine actions and twelve samples each; use
its own baker and handoff for exact dimensions and stage assembly.

Oaven's 360 frames, Spawner's 192, Kon's 96, Mangler's 216 and Serpent's 648 are
BAKED playback counts. They are not those numbers of separately painted poses.
Current painted characters use one principal view and mirrored facing, not an
eight-direction character set. Do not advertise either capability inaccurately.

## 7. Ground Anchors And The 3D Battlefield

Implementation: [map_3d_view.gd](../../scripts/map/map_3d_view.gd) and the unit's
painted art script, for example
[mangler_painted_art.gd](../../scripts/units/mangler_painted_art.gd).

The live Sprite2D owns texture, hframes, vframes and frame selection. The shared
Sprite3D presentation mirrors that atlas/frame information into the 3D view.
The same animation logic drives both views; no second rig is needed.

Metadata includes billboard_pixel_size and foot_anchor_y. The bridge adjusts
vertical placement using:

```text
(foot_anchor_y - half_frame_height) * billboard_pixel_size
```

The purpose is to align the painted feet, not the center of the image, to the
unit's simulation position and authored navigation elevation. Keep 2D offset,
3D pixel size, frame height and foot metadata consistent.

Mangler uses foot_anchor_y=330, a 384px frame, 2D scale 0.48, offset.y=-138 and
billboard pixel size 0.0075. Spawner and Oaven use different measured values.
These are asset-specific contracts, not universal constants to copy blindly.

During Mangler's leap the art offset and foot metadata include the visual
height. The mechanic still owns the valid target, landing and collision policy.
An airborne-looking sprite alone does not turn a ground unit into a flyer.

## 8. Runtime State Selection And Combat Timing

The art script reads actual unit state: movement, health change, attack event,
evolution and ability phase. It computes row and frame; it does not apply damage.

Mangler's present implementation advances its motion clock with momentum,
uses the last melee attack timestamp for attack playback and prioritizes leap
phase over lower-priority reactions. Review the current script before changing
timing; not every unit uses the same event source or priority order.

Spawner's successful shot/drone callbacks trigger corresponding visual clips;
root/unroot and flight transitions follow cast progress. These are stronger
signals than guessing from a target merely being nearby.

For a new clip, explicitly write down:

- Triggering authoritative event or state.
- Windup, contact/release and recovery times.
- Loop or one-shot; final frame behavior.
- What interrupts it and which state takes precedence.
- Whether movement changes facing during the action.
- What happens on evolution, stun, banishment and death.

Existing code uses different clock mechanisms in different units. Match the
unit's gameplay clock; do not substitute wall-clock timing for simulation
timing without testing pause, speed and interruption behavior.

## 9. Death Animation And Visual Effects

Relevant files: [painted_unit_death.gd](../../scripts/fx/painted_unit_death.gd),
[oaven_death_sprite.gd](../../scripts/fx/oaven_death_sprite.gd), and the painted
death handling in map_3d_view.gd.

When gameplay removes a unit, a visual-only object can retain its texture and
death row long enough to collapse, hold and fade. It must not remain a living
unit, grant vision, block movement or receive further combat targeting.

The art metadata tells the presenter death_row, death_seconds and corpse hold
duration. Existing unit contracts differ. Do not free the sprite before its
corpse has copied the needed visual state; clean up auxiliary 3D objects too.

VFX combine existing painted textures and procedural rendering: ground rings,
spores, short streaks and impact indicators. Rendering code is appropriate for
these timed effects. It is not a substitute for the painted character source.
Damage and resource consumption occur once in gameplay, never again in FX.

Check visibility against fog/banishment and correct floor height. A status pip
or lingering effect must not accidentally reveal a hidden unit.

## 10. Building Image Generation And Materials

Buildings use real 3D geometry rather than unit-style baked pose atlases.
The generator provides selected production textures, and skin code constructs
walls, arches, supports, windows, doors, floors and identity props.

The vault's [library_atlas.png](../../assets/structures/observer_vault/library_atlas.png)
contains four regions: bookshelves, engraved circular door, cyan eye seal and
slate. It is an opaque texture atlas, not a transparent animation sheet.

The skin's _atlas_material selects quadrants using UV scale 0.496 and a 0.002
inset from each quadrant origin. This provides a small sampling margin. That
specific inset is not a guarantee against every mip/texture filter condition;
inspect at near and distant views when changing resolution/import settings.

The round door is actual geometry with painted circular faces, attached to a
hinge node. The eye seal has an emissive material and a nearby light. Windows
reuse the established gothic glass treatment, framing and lantern lights.

The lab/vault share painted masonry and deterministic primitive construction.
Repeated primitives are batched where appropriate. Seeded variation makes
rebuilds stable while avoiding perfectly uniform masonry silhouettes.

The appearance comes from geometry + painted surfaces + framing + light, not
from stretching the original concept image across a block. Cyan emission alone
does not produce local light spill under every renderer configuration.

## 11. Buildings: Animation Must Respect Navigation

The current vault door immediately rotates to its open or closed orientation.
It is not a timed opening animation. When open it parks in an authored reserved
bay; navigation never assumes that bay is a walkable aisle.

Adding a future animated door requires deciding when the passage becomes
traversable, handling interrupted opening and keeping collision/state/visuals
synchronized. Do not tween a door separately while leaving the navigation key
in an incompatible state.

Units can enter because YAML independently describes floors, links, gates and
clearances. Texture generation has no role in deciding walkability. Downsizing
requires a redesigned layout at the target dimensions, not blindly scaling
all coordinates and decorations. See [BUILDINGS.md](BUILDINGS.md).

## 13. Quality Control And Common Failure Modes

| Symptom | Likely area to inspect |
| --- | --- |
| Magenta edge / checkerboard | Source alpha, key shader, contaminated edge colors |
| Floating fragments | Incorrect source rectangles or neighbouring-pose overlap |
| Limb rotates unnaturally | Joint origin and local drawing rectangle |
| Feet slide or float | Pose fit, foot anchor, sprite offset, 3D scale |
| Clipped wings/death pose | Largest silhouette versus frame padding |
| Duplicate / blank baked frames | Redraw and frame_post_draw waits |
| Last pose never appears | One-shot phase denominator and runtime clamping |
| Attack looks unrelated to impact | Event trigger and contact timing |
| New form loses upgrades | Gameplay evolution path, not atlas code |
| Corpse still targetable | Unit registration versus visual-only death object |
| 2D good, 3D wrong | Shared bridge metadata, billboard scale, floor transform |
| Glowing rectangle instead of window | Framing, texture contrast, emission and lights |
| Walkable cells inside decoration | Missing occupancy reservation or skin intrusion |
| Preview good, game still old art | Catalog, factory/scene, builder dispatch, import |

Inspect actual playback and actual map screenshots. Contact sheets show poses,
not temporal quality. Pixel checks show content, not artistic success. Compare
to an approved asset at the same camera distance and lighting.

Keep atlases shared, not generated for each runtime instance. Width * height *
4 gives the uncompressed RGBA8 byte estimate before mipmaps. Extra frames and
forms are real memory costs, not free quality. Do not change compression or
filtering globally to fix one asset without checking other art.

## 14. Exact Instructions For Another LLM

1. Read this file and the relevant existing unit/building handoff.
2. Confirm reference access, image-tool access, renderer access and write scope.
3. Preserve the current gameplay contract and choose parts versus key poses.
4. Request production art, archive the result and inspect actual pixels.
5. Author regions/pivots/timing; never guess source-grid boundaries blindly.
6. Bake a vertical slice and inspect it at gameplay scale before filling out
   every state. Keep the approved source so rebuilds do not require regeneration.
7. Complete the action set or building interior and integrate normal game paths.
8. Run focused and live tests, review animations and save evidence.
9. Hand off source prompt, region map, baker, runtime contract, commands,
   screenshots, logs and honest limitations.

If image tools are unavailable, prepare code/contracts only and explicitly
leave the art blocked. If visual inspection is unavailable, leave visual
acceptance to a capable reviewer. Never replace missing production artwork with
placeholder polygons and declare it equivalent to the user's reference.

Use [OVERNIGHT_AGENT.md](OVERNIGHT_AGENT.md) for bounded unattended work. This
document records the workflow; it does not authorize spending or scheduling.
